# 虚拟通道（无驱动进程级路由）——设计、验证与边界

> 版本：v1.0.0　　实机验证：2026-11-04（本机 Win11 26200 / .NET 8）
> 目标：让「只在启动时读一次输出设备」的程序也能跟着窗口走，并且把控制粒度做到**每个进程**。

---

## 1. 原来的问题到底卡在哪

现有能力（直连模式）是给进程设「默认输出设备」：

```
程序窗口在 DISPLAY6 → 映射到 HDMI 端点 → SetPersistedDefaultAudioEndpoint(pid, HDMI)
```

这招对大部分程序有效，但对一类程序无效：**它们启动时读一次设备就锁死了**，
运行中改策略不会迁移已经在播的音频流（某手游模拟器客户端就是实测例子）。
之前的办法只有两个：

1. 重启那个程序（策略是持久化的，重启后就用上了）；
2. 用「固定」+ 看门狗，在它启动时先把策略设好。

第 2 条还有一个实测出来的硬限制（这次才确认）：

> `SetPersistedDefaultAudioEndpoint` 对一个**还没有音频会话**的进程返回
> `E_INVALIDARG (0x80070057)`（notepad / mspaint 实测）。
> 也就是说「进程一出现、还没出声就预置」并不成立 —— 必须等它至少创建过一路音频会话。

于是「拖窗口 → 声音跟着走」对这类程序天然做不到：它一旦出声，设备就已经定死了。

---

## 2. 虚拟通道的架构

核心想法：**不要让程序跟着窗口换设备，让「出口」跟着窗口换。**

```
          ┌─────────────┐   钉一次（永久）   ┌──────────────┐
 程序 A ──┤ 静音虚拟声卡 ├─────────────────→│ 进程回环捕获  │──┐
 程序 B ──┤ (CABLE 等)  ├─────────────────→│ 进程回环捕获  │──┤
 程序 C ──┤             ├─────────────────→│ 进程回环捕获  │──┤
          └─────────────┘                   └──────────────┘  │
                                                              ▼
                                          抖动缓冲（200 ms）→ 渲染到「窗口所在显示器的设备」
                                          目标随时可换，程序无感
```

三个部件：

| 部件 | 实现 | 说明 |
|---|---|---|
| 静音虚拟声卡 | 任选现成的（VB-Cable `CABLE Input` / VoiceMeeter / Virtual Audio Cable），按**名称**识别 | 未来的自研驱动也走同一识别规则（名字里带 `VideoTurner`） |
| 每进程捕获 | `Windows 10 2004+` 的 **Process Loopback**：`ActivateAudioInterfaceAsync` + `VAD\Process_Loopback` + `AUDIOCLIENT_ACTIVATION_TYPE_PROCESS_LOOPBACK` | 只抓指定进程树，**与它把声音送到哪台设备无关** |
| 每进程渲染 | WASAPI 共享模式 + `AUDCLNT_STREAMFLAGS_AUTOCONVERTPCM \| SRC_DEFAULT_QUALITY` | 格式/采样率交给 Windows 转，换设备不用重采样 |

### 为什么这样就治好了「只读一次」

虚拟声卡的端点 ID 是**永久稳定**的。程序第一次被纳入时重启一次，从此它每一次启动都读到同一个设备
（实测：策略按可执行文件持久化，同一个 exe 的**新实例**一出声就直接落在虚拟声卡上），
之后窗口在两台显示器之间怎么拖，都只是我们在下游换出口 —— 程序完全察觉不到。

### 数据流细节

- 捕获格式固定 `48000 Hz / 2 ch / float32`（带 AUTOCONVERTPCM，引擎自己从虚拟声卡混音格式转）
- 环形缓冲 200 ms：写满丢最旧（防延迟累积），读空补静音（记一次欠载）
- 目标解析：**按应用固定 > 窗口所在显示器的映射 > 系统默认设备**
  （最后一条是刻意的：虚拟模式下不能「没有出口」，否则等于静音）
- 换出口只重建渲染端，捕获不断流（约 100 ms 空档）
- 退出时会把托管程序在虚拟声卡上的固定项清掉 —— 否则本程序没在跑的时候，那些程序会把声音送进静音端点，等于全哑

## 3. 实机验证（`tools\LoopbackProbe`）

```
LoopbackProbe.exe                # 抓一个子进程的音频 → 渲染到另一台设备，量目标端点回环电平
LoopbackProbe.exe --channel-test # 完整流程：钉到虚拟声卡 → 捕获渲染 → 重启后落点检查
```

`--channel-test` 在本机的实测输出（2026-11-04）：

```
虚拟声卡（假装是静音端点）：扬声器 (板载声卡)
原设备（程序本来在用的）：HDMI (NVIDIA High Definition Audio)

1) 程序 A（PID 26964）当前会话设备：HDMI (NVIDIA High Definition Audio)
   写入后读回：\\?\SWD#MMDEVAPI#{0.0.0.00000000}.{55f01aa4-…}#{e6327cad-…}

2) 把 A 的音频抓下来，送到另一台设备（A 不重启）
   通道：ToneA (PID 26964) → 扬声器 (板载声卡)；捕获 3.1s，峰值 0.337
   目标端点回环峰值：0.488

3) 重启同样的程序，看它是不是直接落在虚拟声卡上
   程序 B（PID 27552）会话设备：扬声器 (板载声卡)

✅ 虚拟通道成立
```

三条结论都有数据支撑：
1. 改一个**正在出声**的进程的设备：成功，且读回一致；
2. **不重启**那个进程，也能把它的音频抓下来、送到另一台设备（目标端点确实收到了有声数据）；
3. 同一个 exe 的**新实例**一启动就落在虚拟声卡上 —— 这是「重启一次，之后永远听话」的证据。

另一支探针（`LoopbackProbe.exe` 默认模式）还量了目标端点回环：捕获峰值 0.337 → 目标端点 0.382，链路通。

## 4. 代码落点

| 文件 | 作用 |
|---|---|
| `Interop/WasapiInterop.cs` | 进程回环的激活（`ActivateAudioInterfaceAsync`，注意导出在 `mmdevapi.dll`）、IAudioClient / IAudioCaptureClient / IAudioRenderClient 裸接口、`AudioFormat` |
| `Services/ProcessLoopbackCapture.cs` | 每进程捕获线程（轮询包，算峰值） |
| `Services/WasapiDeviceRenderer.cs` | 共享模式渲染线程（AUTOCONVERTPCM，10 ms 写循环） |
| `Services/AudioRingBuffer.cs` | 200 ms 环形缓冲（丢最旧 / 补静音） |
| `Services/ProcessChannel.cs` | 一路通道 = 捕获 + 缓冲 + 渲染；换出口只重建渲染 |
| `Services/VirtualChannelEngine.cs` | 通道集合的增删改（幂等，每周期调一次） |
| `Services/VirtualSinkService.cs` | 按**名称**识别虚拟声卡；名称里带显示器型号的虚拟端点还能被「自动匹配」认到那台显示器 |
| `Services/RoutingEngine.cs` | 虚拟模式分支：钉到虚拟声卡、登记通道、目标解析 |
| `ViewModels/MainWindowViewModel.cs` + `Views/MainWindow.xaml` | 设置页「虚拟通道」卡片：开关 / 虚拟声卡选择 / 纳入当前程序 / 托管列表；诊断报告加「虚拟通道」一节 |

## 5. 使用方式（用户视角）

1. 装一台虚拟声卡（VB-Cable 即可，它默认就是静音输出端点）；
2. 设置页 →「虚拟通道」→ 打开开关 → 选中那台虚拟声卡（点「重新扫描」能刷新）；
3. 点「纳入当前正在出声的程序」，或让它自动纳入（第一次路由到某个程序时会自动加入托管列表）；
4. 该程序**重启一次**。这次它的声音进了虚拟声卡，我们在下游把它送到「窗口所在显示器」的设备；
5. 以后拖窗口：只换出口，**不用再重启**；每个程序各自一路，互不影响。

状态行会明确写出当前处于哪一步，例如：

- `QQMusic：已指向虚拟通道「CABLE Input」，但它当前仍直接播在「扬声器」—— 重启该程序后就会走虚拟通道（此后拖窗口不用再重启）`
- `虚拟通道建立：QQMusic (PID 1234) → HDMI (NVIDIA High Definition Audio)（捕获 48000 Hz / 2 ch / 32 bit float）`

## 6. 已知边界与后续

1. **必须有虚拟声卡**。没有它，虚拟模式不生效（界面会写明），直连模式照旧可用。
   自研驱动（`SysVAD` 派生，MIT 示例）是下一步；本机没装 WDK / 没有签名环境，**这次没有动驱动**。
   自研驱动的好处：端点名字可以带显示器型号（`VideoTurner Virtual — U2720Q`），
   多个端点时可以做到「一台显示器一个端点」，且安装包可控。
2. **首次纳入要重启一次**。因为无会话的进程无法预置策略（见第 1 节实测），这是 Windows 的限制。
   策略持久化之后就不再需要重启。
3. **退出 VideoTurner 会还原托管程序的设备**（安全考虑）。若想「永不还原」，把 VideoTurner 设为开机自启并常驻即可。
4. **关掉「音频路由」开关时，已经建立的虚拟通道会继续工作**（把声音送到上一次的目标）——
   因为那些程序已经落在虚拟声卡上了，停掉捕获就等于静音。想真正回到直连：先关虚拟通道，
   再重启那些程序（固定项会被还原）。
5. **换一台虚拟声卡需要重新走一遍「重启一次」**：程序还在旧虚拟声卡上，新端点不会自动接管。
6. **延迟**：捕获 20 ms + 环形缓冲 200 ms + 端点 100 ms，实际约 0.2–0.3 s。听音乐/看视频可接受，音游不合适。
7. **受保护内容 / DRM 音频**可能不允许回环捕获（与 OBS 的应用音频捕获同源限制）。
8. 每路一个捕获 + 一个渲染线程；十几路没问题，几十路要再评估。
9. 目前不做每程序音量（会话音量在虚拟声卡上，调它会影响捕获后的一路；要做得在渲染端加增益）。

## 7. 为什么不是「自己写一个用户态虚拟设备」

Windows 没有用户态虚拟音频端点这条路：音频端点必须由内核态 PortCls/AVStream 驱动创建
（UMDF 不支持音频）。所以只有两种选择：

- 用现成已签名的虚拟声卡（本方案，今天就能用）；
- 自己写 WDM 驱动（`Windows-driver-samples/audio/sysvad`，MIT 示例），需要 WDK + 测试签名或 EV 证书，
  并且要 `bcdedit /set testsigning on` + 重启。**本机没有 WDK，这一步这次没做。**
